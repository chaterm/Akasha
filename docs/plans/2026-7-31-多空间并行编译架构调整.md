# 多空间并行编译架构调整实施方案

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 支持一次提交最多 100 个空间编译，由多个同构实例消费固定共享队列；默认 3 个实例、每实例最多并行 10 个空间阶段时间片，实例扩容时集群吞吐量自然增长，同时保证同一空间的 canonical knowledge 发布严格串行。

**Architecture:** PostgreSQL 中的 `CompileRun`/`RunPage`/`RunImage` 是持久化事实来源，BullMQ 只负责分发。空间文字编译和图片知识合并使用共享空间队列，以“一个空间阶段的一个可恢复时间片”为物理 Job 粒度；每个时间片最多处理 5 个页面或运行 5 分钟，在页面 checkpoint 后释放空间槽并通过 continuation Job 恢复。图片理解使用共享图片队列，改为每张图片一个物理 Job；图片结果先落库，页面/空间图片屏障完成后再进入可恢复的空间级串行合并。

**Tech Stack:** NestJS 11、BullMQ 5、Kysely/PostgreSQL、React 18、Mantine 8、TanStack Query、Jest、Vitest。

## 1. 状态与已经确认的架构决策

本文档是 2026-07-31 的可实施版本。以下决定已经确认，不在第一版实施中继续摇摆：

1. 所有空间共享固定队列，不为每个空间创建物理队列。
2. 所有编译实例都是同构消费者，可以消费任意空间任务。
3. 默认部署 3 个编译实例。
4. 每个实例的空间任务并发可以配置，范围为 1～10，默认 10。
5. 不设置 BullMQ 集群级 global concurrency；增加实例会增加系统并发。
6. 一个空间执行槽只执行一个空间阶段时间片，但一个实例可以提供最多 10 个空间执行槽。
7. 同一空间的文字页面编译和 canonical knowledge 发布保持串行。
8. 图片理解不直接发布 canonical knowledge，可以在空间之间、页面之间共享并行。
9. 图片结果持久化后，由数据库屏障触发一个空间级图片合并逻辑阶段；该阶段可产生多个串行 continuation 时间片，空间不会轮询或阻塞等待图片队列。
10. PostgreSQL 是编译状态和历史的事实来源；Redis/BullMQ 是可恢复的执行传输层。
11. canonical artifact 的所有权严格限定为 `(workspaceId, spaceId)`；跨空间引用不是跨空间共享 artifact。
12. 空间长任务显式配置 BullMQ 锁续期和 stalled 策略；`heartbeat_at` 只用于数据库可观测性，不承担 BullMQ 续锁。
13. 文字和图片合并的逻辑阶段可以跨多个物理 Job；每个 Job 是可恢复时间片，默认最多 5 页或 5 分钟，在安全页面边界主动让出空间槽。
14. BullMQ priority 不抢占 active Job；可控等待来自时间片主动让出，不来自 `priority=1` 本身。
15. 本方案只实现并运行新空间编译协议，不设计旧 Run、旧编译 Job 或旧 handler 的运行期兼容；上线后对已有空间统一触发 `force_rebuild` 属于运维动作，不属于稳态架构。
16. 每个图片 Job 只处理一张图；不允许一个页面内 50 次 VLM 调用串行占用同一图片槽。
17. 每个空间页面操作有 15 分钟硬 deadline，initial/final aggregate 各有 5 分钟总 deadline，每个单图 Job 有 3 分钟硬 deadline；超时后不得继续 publication。
18. 默认每实例数据库连接池为 25，并发扩容必须同时满足 PostgreSQL 总连接预算；“不设应用级全局并发上限”不等于数据库容量无上限。
19. 图片队列的 completed/failed Job 必须在 reaper 窗口内有界保留；`missing` 是异常交通层信号，最多重投 3 次并告警，不是常规调度路径。
20. 空间和单图 reaper 都在 expiry 后再查 exact BullMQ Job 状态；单凭 heartbeat/lease 过期不得终结任务。
21. 普通内容更新/编译请求不再 supersede 活动 Run：未初始化 queued Run 只 coalesce，已初始化活动 Run 只记录一个 `rerun_requested`；source set 删除属于 fail-closed replan，不走普通内容更新分支；只有显式 force/reset 能创建 superseding Run。
22. removed source 的检索失效与物理 contribution 清理解耦：请求/删除事件先 fail-closed 失效受影响 source 和 canonical 产物，Worker 初始化后再删除 contribution、计算孤儿并重建。

默认容量为：

```text
3 个实例 × 10 个空间槽 = 30 个空间阶段时间片并行
3 个实例 ×  5 个图片槽 = 15 个单图任务并行
```

增加到 4 个实例后，无需修改集群级配置：

```text
4 × 10 = 40 个空间阶段时间片并行
4 ×  5 = 20 个单图任务并行
```

第一版不引入全局令牌桶、空间专属 Worker、Worker 所有权分片或通用工作流引擎。

## 2. 目标与非目标

### 2.1 目标

- 一次 API 请求最多接受 100 个去重后的空间 ID。
- 100 个空间都能持久化进入等待或运行状态，而不是要求 100 个实例。
- 3 个默认实例最多同时执行 30 个空间阶段时间片，其余空间由 BullMQ 排队。
- 增加实例后容量按实例本地并发之和增长。
- 大空间不能通过文字页面 fan-out 淹没文字队列。
- 同一空间的页面不能并发修改同一个 canonical artifact。
- 图片提取跨空间共享计算资源，同时避免一个超大空间把图片队列一次填满。
- Worker 崩溃后，其他实例能够依据数据库进度继续，而不是从第一页重新开始。
- 大空间每个时间片后回到共享队列尾部，不能连续数小时占有空间槽；等待中的 merge 在下一个槽位释放点优先执行。
- 页面在活动 Run 期间更新时不能被静默丢弃。
- Knowledge diagnostics 能清楚回答：有多少 Run、分别在哪个阶段、空间槽/图片槽使用多少、哪个空间或页面失败。
- 明确接受单个大空间从当前最多占用多个页面 Worker，调整为同空间固定串行后端到端耗时可能增加；第一版优先保证 100 个空间的总吞吐、公平性和 canonical 一致性。

### 2.2 非目标

- 不保证 100 个空间在同一时刻全部执行。
- 不对所有实例设置集群级并发硬上限。
- 不在第一版实现基于 CPU、内存或供应商配额的动态并发调节。
- 不把图片 OCR、caption 或页面正文放入 Redis 作为返回结果。
- 不重写现有 artifact、contribution、generation fencing 和图片 extraction 缓存模型。
- 不在第一版实现跨空间任务优先级产品配置；只使用固定的内部优先级保证接近完成的 Run 优先收敛。
- 不在页面执行中间强制抢占；时间片只在页面 publication/checkpoint 完成或页面尝试超时后让出。
- 不实现新旧空间编译协议共存、旧队列排空、旧数据清理或回滚到旧编译架构；现有空间上线后统一强制编译。
- 不在第一版通过同空间页面并发优化单个大空间延迟；未来只能先并行不写 canonical 的计算阶段，canonical materialization/publication 仍必须串行或增加 contribution revision fence。

## 3. 当前实现

### 3.1 当前队列和并发

当前有两个知识编译队列：

```text
QueueName.KNOWLEDGE_TEXT_QUEUE  = {knowledge-text-queue}
QueueName.KNOWLEDGE_IMAGE_QUEUE = {knowledge-image-queue}
```

关键位置：

- `apps/server/src/integrations/queue/constants/queue.constants.ts`
- `apps/server/src/integrations/queue/queue.module.ts`
- `apps/server/src/ee/llm-wiki/processors/knowledge-text.processor.ts`
- `apps/server/src/ee/llm-wiki/processors/knowledge-image.processor.ts`

当前每个实例：

```text
文字 Worker concurrency = 2（硬编码）
图片 Worker concurrency = 5（硬编码）
```

文字队列混合承载：

- `KNOWLEDGE_COMPILE_SPACE`
- `KNOWLEDGE_COMPILE_PAGES`
- `KNOWLEDGE_MERGE_PAGE_IMAGES`
- `KNOWLEDGE_AGGREGATE_SPACE`
- embedding rebuild
- access reindex
- stale maintenance
- `PAGE_CONTENT_UPDATED`（Hocuspocus 持久化触发）
- Review 等任务

### 3.2 当前空间编译流程

当前 `KNOWLEDGE_COMPILE_SPACE` 只完成空间导出和 `startSpaceRun()`，随后立即返回 `queued`。真正的文字编译由 `KnowledgeSpaceCompilationService.dispatchPending()` 扫描数据库并逐页投递：

```text
compile-space
  -> exportSpaceSources
  -> startSpaceRun
  -> 创建 Run / RunPages
  -> dispatchPending 查询 pending RunPages
  -> 每页一个 KNOWLEDGE_COMPILE_PAGES Job
  -> 文字页面屏障
  -> initial aggregate Job
```

`findPendingPageDispatches()` 当前全局按 `run_page.created_at ASC` 取前 100 条，不按空间分组。一个大空间可以在较长时间内占据队列前部。

当前 `findLatestRunForAggregateReuse()` 只有空间过滤和 `created_at DESC`，没有终态过滤，也没有排除当前 Run。现流程能工作，是因为 `createRun()` 在插入新 Run 前调用它；目标流程改成“先创建 queued 占位 Run，Worker 再初始化”后，如果原查询原样复用，最新一行将永远是当前 queued Run，aggregate reuse 会静默永久关闭。目标实现必须把查询契约改成“排除 currentRunId，且只返回 `status IN ('succeeded','partial') AND phase='complete'` 的历史 Run”。

### 3.3 当前图片流程

当前图片设计已经具备 extraction cache、snapshot/generation fence 和完成屏障等可保留基础，但物理 Job 过大：

```text
文字与 initial aggregate 完成
  -> Run phase = images
  -> 每个含图片页面一个 KNOWLEDGE_COMPILE_PAGE_IMAGES Job
  -> 页面内最多 50 张图串行处理，最坏外部调用为 50 × 120s
  -> OCR/caption 保存到 knowledge_image_extractions
  -> 每页再投递一个 KNOWLEDGE_MERGE_PAGE_IMAGES 到文字队列
  -> 所有页面 merge 终态
  -> final aggregate
```

图片任务已经使用 source version、content hash、attachment version、knowledge generation 和 extraction claim 约束陈旧任务，图片页面任务最多重试 3 次。但单个 Job 可持续约 100 分钟，会造成图片队列不公平、长时间占槽和困难的 stalled 恢复。目标架构因此保留缓存与 fence，但把物理调度粒度改为单图。

问题不在图片 extraction 本身，而在 extraction 之后的 canonical knowledge 合并仍然是“一个页面一个文字队列 Job”。对于带 `spaceRunId` 的 Run-scoped merge，当前 publication transaction 已经通过 `isRunActiveForPublication()` 对 `spaces` 行执行 `FOR UPDATE`，所以同一空间的事务写入段实际会串行；不能把竞态简单归因为“缺少空间锁”。

真正的竞态窗口位于事务和空间行锁之前。`KnowledgeImportService.importCompileResult()` 会先读取 previous/affected contributions，再由 `KnowledgeArtifactMaterializerService` 基于该快照执行 canonical materialization，必要时调用 LLM 合并。完成 artifact、chunk 和 embedding 等待发布数据的构造后，代码才进入 `executeTx()`，并在 publication guard 中获取 `spaces FOR UPDATE`。后获得锁的事务不会重新读取 contributions，也没有校验“物化时读取的 contribution revision 是否仍是当前版本”，而是直接写入锁外已经生成的 canonical artifact。

因此，P1、P2 两个页面 merge 仍可能同时基于旧 contribution 快照生成 M1、M2；P1 先在锁内发布，P2 随后取得锁，但仍用旧快照生成的 M2 覆盖 canonical artifact。最终 contribution 行可能都已经是新版本，canonical 正文却没有反映所有最新 contribution。Standalone merge 没有 Run-scoped publication guard，保护更弱。目标架构必须消除并发的“读取 contribution → LLM 物化 → 发布”链路，而不是再补一把已经存在的空间行锁。

### 3.4 当前 Diagnostics

当前 `KnowledgeDiagnosticsService.getWorkspaceDiagnostics()` 同时组装页面、Run、Redis Job、队列、质量、隔离和检索信息。主要扩展性问题：

- Redis `getJobs()` 后再按 workspace/space 过滤。
- 最多 50 个 Run 的全部 RunPage 行加载到 Node.js 后聚合。
- 客户端默认每 5 秒轮询整个诊断响应。
- 页面、Run、队列和质量信息在一个长页面内一起刷新。
- 队列完成/失败 Job 默认会删除，因此 Redis 历史本身也不能作为可靠事实来源。

关键位置：

- `apps/server/src/ee/llm-wiki/services/knowledge-diagnostics.service.ts`
- `apps/server/src/ee/llm-wiki/llm-wiki.controller.ts`
- `apps/client/src/ee/llm-wiki/pages/knowledge-admin.tsx`
- `apps/client/src/ee/llm-wiki/services/knowledge-service.ts`

## 4. 当前方案与目标方案对比

| 维度 | 当前实现 | 调整后 |
|---|---|---|
| 文字调度单位 | 一个页面一个 Job | 一个空间文字阶段拆为多个可恢复时间片 Job |
| 空间初始化 Job | 只创建 Run | 首个时间片创建/恢复 Run，后续时间片从 RunPage checkpoint 继续 |
| 同空间文字并发 | 可能大于 1 | 固定为 1 |
| 单个大空间延迟 | 可占用多个文字 Worker，理想页面吞吐较高 | 可能增加；接受该取舍以换取多空间公平性和一致性 |
| 跨空间并发 | 页面混在共享队列 | 空间任务直接占用共享执行槽 |
| 每实例空间并发 | 文字队列硬编码 2 | 环境变量配置 1～10，默认 10 |
| 数据库连接池 | 全进程共享单池，默认 10，无 validation/部署示例 | 默认 25，校验本实例并发预算，上线前校验全集群 `max_connections` |
| 集群并发 | 实例数 × 2 | 实例本地并发之和，不设 global cap |
| 100 空间任务量 | 空间 Job + 大量文字页面 Job | 每个空间同一时刻最多一个 DB 有效时间片 reservation；文字页面不单独进入 Redis |
| 图片提取 | 共享图片队列，一页一 Job，页内最多 50 张串行 | 一图一 Job + RunImage 持久化 outbox，按 Run 最多 outstanding 5 |
| 图片快照 | dispatcher 投递前重新导出，多处覆写父计数 | init 一次冻结 RunImage，cache hit 写 succeeded 子行，dispatcher 只读 DB |
| 图片结果 | 落数据库 | 保持落数据库，不通过 Redis 返回大结果 |
| 图片知识合并 | 每页一个文字 Job；Run-scoped 写入事务虽有空间行锁，但锁外 contribution 读取/LLM 物化可并发且无 revision fence | 一个空间合并逻辑阶段，使用可恢复时间片逐页完成“读取、物化、发布”完整链路 |
| 聚合 | initial/final 独立 Job | 保留两个阶段语义，在完成页面屏障的最后一个空间时间片内执行 |
| 页面更新遇到活动 Run | 直接跳过 | queued Run 合并请求；running Run 设置 rerunRequested |
| 故障恢复 | 页面 Job 粒度 | RunPage checkpoint + 当前时间片重试/continuation |
| 孤儿任务 | 无非终态 Run 扫描器 | lease expiry 候选 + exact Job 状态判定 + recovery lease + 唯一 `finishRun()` |
| Redis 终态 Job | 图片队列 completed/failed 立即删除 | 有界保留供 exact-state reaper 判定，missing 最多恢复 3 次 |
| Diagnostics | Redis Job 视角为主 | DB Run/阶段/进度为主，Redis只表示实时容量 |

默认 3 个实例时，当前文字队列 `concurrency=2` 允许一个大空间理论上占用最多 6 个页面 Worker；新架构把同空间 canonical 链路固定为 1。因此在页面耗时相近、无其他瓶颈的理想模型下，单个大空间的文字阶段最坏可能接近 6 倍耗时，高负载下还要叠加时间片重新排队。实际耗时取决于 provider、缓存和复用率，但本方案不隐藏这一方向性退化：它用单空间延迟换取 100 空间的集群总吞吐、公平性和可证明的一致性。

## 5. 目标拓扑

### 5.1 固定队列

编译链路使用两个固定共享队列：

```text
KNOWLEDGE_SPACE_QUEUE
  - KNOWLEDGE_COMPILE_SPACE_TEXT
  - KNOWLEDGE_MERGE_SPACE_IMAGES

KNOWLEDGE_IMAGE_QUEUE
  - KNOWLEDGE_COMPILE_IMAGE
```

原 `KNOWLEDGE_TEXT_QUEUE` 继续存在，但只承载非空间编译维护任务：

```text
KNOWLEDGE_REBUILD_EMBEDDINGS
KNOWLEDGE_REINDEX_ACCESS
KNOWLEDGE_MARK_SOURCES_STALE
PAGE_CONTENT_UPDATED
REVIEW_DISCOVER
REVIEW_NEGOTIATE
```

新版本不再为旧的空间编译 Job 注册生产路径；这样可以避免空间长任务阻塞 reindex、embedding 和 Review，并保持只有一套空间编译协议。`PAGE_CONTENT_UPDATED` 必须保留：它是 Hocuspocus 持久化路径的独立触发入口，handler 继续执行 access reindex，但把旧的 `KNOWLEDGE_COMPILE_PAGES` 投递改为统一的空间增量 Run 请求。

### 5.2 实例模型

每个编译实例注册：

```text
KnowledgeSpaceProcessor concurrency = KNOWLEDGE_SPACE_CONCURRENCY
KnowledgeImageProcessor concurrency = KNOWLEDGE_IMAGE_CONCURRENCY
```

配置定义：

```env
KNOWLEDGE_SPACE_CONCURRENCY=10
KNOWLEDGE_IMAGE_CONCURRENCY=5
KNOWLEDGE_SPACE_SLICE_MAX_PAGES=5
KNOWLEDGE_SPACE_SLICE_MAX_MS=300000
KNOWLEDGE_SPACE_HEARTBEAT_MS=30000
KNOWLEDGE_SPACE_LEASE_TTL_MS=180000
KNOWLEDGE_PAGE_DEADLINE_MS=900000
KNOWLEDGE_AGGREGATE_DEADLINE_MS=300000
KNOWLEDGE_IMAGE_JOB_DEADLINE_MS=180000
KNOWLEDGE_COMPILER_TIMEOUT_MS=120000
DATABASE_MAX_POOL=25
DATABASE_STATEMENT_TIMEOUT_MS=30000
```

校验规则：

```text
KNOWLEDGE_SPACE_CONCURRENCY: integer, min=1, max=10, default=10
KNOWLEDGE_IMAGE_CONCURRENCY: integer, min=1, max=10, default=5
KNOWLEDGE_SPACE_SLICE_MAX_PAGES: integer, min=1, max=50, default=5
KNOWLEDGE_SPACE_SLICE_MAX_MS: integer, min=60000, max=900000, default=300000
KNOWLEDGE_SPACE_HEARTBEAT_MS: integer, min=10000, max=60000, default=30000
KNOWLEDGE_SPACE_LEASE_TTL_MS: integer, min=120000, max=600000, default=180000
KNOWLEDGE_PAGE_DEADLINE_MS: integer, min=300000, max=900000, default=900000
KNOWLEDGE_AGGREGATE_DEADLINE_MS: integer, min=60000, max=600000, default=300000
KNOWLEDGE_IMAGE_JOB_DEADLINE_MS: integer, min=120000, max=300000, default=180000
KNOWLEDGE_COMPILER_TIMEOUT_MS: integer, min=10000, max=600000, default=120000（现有配置）
DATABASE_MAX_POOL: integer, min=1, max=100, default=25
DATABASE_STATEMENT_TIMEOUT_MS: integer, min=5000, max=120000, default=30000
```

这些值会参与 `@Processor()` decorator 求值，不能依赖 Nest 容器创建后的 `ConfigService`。当前启动顺序已满足 decorator 取值需求：

```text
生产：OS env 或 loadRuntimeConfiguration() 加载 Consul
开发：main 动态 import AppModule
  -> AppModule 的静态 import 先求值 EnvironmentModule/ConfigModule.forRoot()
  -> ConfigModule 保持 expandVariables=true 并将 .env 写入 process.env
  -> app.module.ts 再 require EE module
  -> Processor decorator 读取并冻结 knowledge-worker-settings
```

不扩展 `loadRuntimeConfiguration()` 去手工预加载 `.env`；这会重复 ConfigModule 的职责，并可能绕过 `expandVariables: true`。`knowledge-worker-settings.ts` 在模块求值时通过纯函数解析一次；缺失值使用文档默认值，非法值直接使启动失败。Processor spec 验证非默认值时，必须在 import 前设置 `process.env`，执行 `jest.isolateModules()` 后再导入；直接顶层 import 只能覆盖默认分支。

`DATABASE_MAX_POOL` 必须加入 `EnvironmentVariables`、`.env.example` 和实际部署配置。启动校验除了验证单值范围，还要验证本实例保守连接预算：

```text
DATABASE_MAX_POOL
  >= KNOWLEDGE_SPACE_CONCURRENCY
   + KNOWLEDGE_IMAGE_CONCURRENCY
   + 10（HTTP、collaboration 和其他队列的本实例余量）
```

默认值因此从当前代码中的 10 调整为 25。这是保守的启动下限，不表示每个 Worker 全程独占一条连接；最终数值仍需要用 HTTP + 其他队列的混合压测验证。全集群还必须在上线前满足：

```text
所有 Akasha/Collaboration 进程的 DATABASE_MAX_POOL 之和
+ 迁移/管理保留连接
<= PostgreSQL max_connections
```

对默认 3 实例和每实例 25 的场景，数据库给所有相关进程分配的总预算必须覆盖 `75 + 保留量`。增加第 4 个实例时必须重新做连接预算，不允许只扩 Worker 不扩数据库容量。

aggregate provider 一次逻辑 `completeMerge()` 最多会执行两次原始 `generateText()`（首次请求 + schema repair），而两次都受 `KNOWLEDGE_COMPILER_TIMEOUT_MS` 约束。启动时必须做跨字段校验，给 embedding、首次 HNSW DDL、link resolve 和 publication 事务保留至少 60 秒：

```text
2 * KNOWLEDGE_COMPILER_TIMEOUT_MS + 60000
  <= KNOWLEDGE_AGGREGATE_DEADLINE_MS
```

默认 `2 * 120000 + 60000 = 300000` 恰好满足。该规则比仅验证 `2 * compilerTimeout < aggregateDeadline` 更严格；任何配置使两次 provider timeout 已经吃满 aggregate deadline 时必须启动失败，不能等运行时才稳定触发 aggregate timeout。

不调用：

```ts
queue.setGlobalConcurrency(...)
```

调整后的 Diagnostics 可以新增 BullMQ `getWorkers()` 查询，检查返回值后按同构配置估算展示容量：

```text
spaceCapacityEstimate = spaceWorkerCount × 10
imageCapacityEstimate = imageWorkerCount × 5
```

当前 `KnowledgeDiagnosticsService` 只调用 `getJobCounts()`，尚未调用 `getWorkers()` 或 `getWorkersCount()`；上述公式是目标实现，不是现状。这两个 API 底层都依赖 Redis `CLIENT LIST`，只能作为近似展示和告警信号。BullMQ 在部分不支持 `CLIENT LIST/SETNAME` 的环境会从 `getWorkers()` 返回 sentinel 信息，直接调用 `getWorkersCount()` 可能把 sentinel 数成 1；因此目标实现调用 `getWorkers()`、识别不支持响应后返回 `unknown`，不能盲信 count。该结果不能参与调度准入、并发限流、Run 状态转换或一致性判断。

第一版要求同一物理队列上的实例使用同构配置。`concurrency`、`lockDuration/lockRenewTime` 真正按 Worker 生效；`stalledInterval`、`maxStalledCount` 虽由每个 Worker 声明，但 stalled 检查通过队列共享的 `stalled-check` key 竞争执行，抢到检查权的 Worker 会把自己的值用于该队列当次扫描。因此同一 `KNOWLEDGE_SPACE_QUEUE` 的所有实例必须保持以下值一致：

```text
KNOWLEDGE_SPACE_CONCURRENCY
KNOWLEDGE_SPACE_SLICE_MAX_PAGES
KNOWLEDGE_SPACE_SLICE_MAX_MS
KNOWLEDGE_SPACE_HEARTBEAT_MS
KNOWLEDGE_SPACE_LEASE_TTL_MS
KNOWLEDGE_PAGE_DEADLINE_MS
KNOWLEDGE_AGGREGATE_DEADLINE_MS
KNOWLEDGE_IMAGE_JOB_DEADLINE_MS
KNOWLEDGE_COMPILER_TIMEOUT_MS
lockDuration
stalledInterval
maxStalledCount
```

异构 Worker 容量和配置上报不在本次范围内。仓库当前没有 server/app 的 Docker Compose、Kubernetes 或 Helm 部署模板，根 `docker-compose.yml` 只定义 PostgreSQL；因此“默认 3 实例”是目标环境的部署参数，不伪装成修改现有仓库模板。所有实例必须由真实部署平台引用同一份环境变量配置，并在上线清单中完成实例数、连接预算和同构配置验收。如果部署资产位于外部运维仓库，对应变更必须作为上线前置条件追踪。

单个空间时间片通常持续数分钟，并可能因为当前页面调用接近超时而超过 5 分钟。Processor 必须显式提供 Worker options，不能只配置 `concurrency`：

```ts
const KNOWLEDGE_SPACE_WORKER_OPTIONS = {
  concurrency: KNOWLEDGE_SPACE_CONCURRENCY,
  lockDuration: 120_000,
  stalledInterval: 30_000,
  maxStalledCount: 2,
};
```

不手工设置 `lockRenewTime`，使用 BullMQ 的默认值 `lockDuration / 2`，即每 60 秒尝试续锁。时间片超过 `lockDuration` 本身不会导致 stalled，只要续锁正常；真正风险是事件循环长时间阻塞、Redis 连接异常或进程暂停导致续锁失败。`120s/30s/2` 是第一版起始值：给瞬时抖动留出余量，同时保证实例真正退出后任务能在数分钟内接管。

`heartbeat_at` 由空间 Runner 每 30 秒在后台定时刷新，并在页面 checkpoint 后立即更新；同一 CAS 将 `execution_lease_expires_at` 续期到 `now + 180s`。启动校验必须保证 `heartbeat < lease TTL`。它不会延长 Redis lock，BullMQ 仍使用自己的锁续期机制。Processor 同时监听并记录 `stalled`、`lockRenewalFailed`、`failed` 事件，告警中必须带 `runId/jobId/workerId/executionToken`。单图 Job 的每次 activation 有 3 分钟硬 deadline，并使用显式锁/stalled 配置和故障注入验收，不再以“任务应该较短”作为可靠性前提。

## 6. 编译状态机

一个逻辑编译仍然对应一个 `knowledge_space_compile_runs`。文字和图片合并各是一个逻辑空间阶段，但可以拆成多个有序的空间时间片 Job；图片提取是若干单图 Job，由 `RunImage` 行聚合成 RunPage 图片屏障。

```text
queued/text
   │ compile-space-text 获取空间槽
   ▼
compiling/text
   ├── initializeRun 发现全量复用、无页面和 aggregate 工作 ──> finishRun() ──> complete
   │
   ├── 达到 5 页/5 分钟且仍有页面 ──> queued/text（continuation loop）
   │
   └── 文字页面屏障完成
               ▼
aggregating/initial_aggregate
   │ initial aggregate 成功
   ├── 无待处理图片 ───────────────> finishRun() ──> complete
   │
   └── 需要图片
          ▼
      compiling/images（释放空间槽，单图任务共享并行）
          │ 图片屏障完成
          ▼
      queued/image_merge
          │ merge-space-images 获取空间槽，priority=1
          ▼
      compiling/image_merge
          ├── 达到时间片预算且仍有页面 ──> queued/image_merge（continuation loop）
          │
          └── merge 页面屏障完成
                      ▼
              aggregating/final_aggregate
                      ▼
      finishRun() -> succeeded / partial / failed，phase=complete
```

说明：

- `compiling/images` 表示 Run 活动但不占用空间 Worker 槽。
- `image_merge` 是新增 Run phase。
- `queued/text` 或 `queued/image_merge` 既可能表示首次等待，也可能表示已初始化 Run 在等待 continuation；`initialized_at` 和 `space_job_sequence` 用于区分。
- 时间片只在页面 publication 和 RunPage checkpoint 已经提交后让出，不在 contribution materialization 中途切断。
- initial/final aggregate 在页面屏障后的最后一个时间片内完成，不做中途抢占；其有独立 5 分钟总 deadline，且单次外部调用继续受 compiler timeout 约束。若未来 aggregate 变成长时间多调用流程，必须独立拆成可排队阶段，不能无限延长最后一个时间片。
- 当前 aggregate 逻辑只调用一次 `completeMerge()`；输入通过 `evenlySample(..., 100)` 和 120k 字符截断吸收空间规模，不随 artifact 数线性增加逻辑 LLM 次数。需要防护的是 provider 内部可能发生首次请求 + 一次 schema repair，因此启动校验按最多两次原始请求计算。
- 如果没有图片，或图片全部命中现有有效知识且无需进入图片异步阶段，允许当前文字空间 Runner 在 initial aggregate 后通过 `finishRun()` 完成。
- 一旦进入 `compiling/images`，图片屏障只能推进 `queued/image_merge`；即使没有成功的图片知识，也由 image-merge Runner 通过 final aggregate 和 `finishRun()` 完成。
- 如果至少一个页面发布了新的图片增强知识，则必须执行 final aggregate。

推荐状态转换表：

| 当前 status/phase | 事件 | 下一状态 |
|---|---|---|
| `queued/text` | 空间 Worker claim | `compiling/text` |
| `compiling/text` | 初始化完成且全量复用、无需 aggregate | `finishRun()` -> `succeeded/complete` |
| `compiling/text` | 时间片预算到达且仍有文字页面 | `queued/text`，清除当前执行租约，等待下一 sequence |
| `compiling/text` | 文字页面屏障完成 | `aggregating/initial_aggregate` |
| `aggregating/initial_aggregate` | 需要图片提取 | `compiling/images` |
| `aggregating/initial_aggregate` | 不需要进入图片阶段 | `finishRun()` -> `succeeded|partial/complete` |
| `compiling/images` | 图片屏障完成且有可合并结果 | `queued/image_merge` |
| `compiling/images` | 图片屏障完成且无可合并结果 | `queued/image_merge`，由短空间时间片收敛 |
| `queued/image_merge` | 空间 Worker claim | `compiling/image_merge` |
| `compiling/image_merge` | 时间片预算到达且仍有 merge 页面 | `queued/image_merge`，清除当前执行租约，等待下一 sequence |
| `compiling/image_merge` | 合并页面屏障完成 | `aggregating/final_aggregate` |
| `aggregating/final_aggregate` | 聚合完成或永久失败 | `finishRun()` -> `succeeded|partial|failed/complete` |
| 任意非终态 | source set 删除/移出空间 | 同一 Run fail-closed replan -> `queued/text`、`initialized_at=NULL`，撤销旧 lease/plan |
| 任意非终态 | 新 Run supersede/force generation 变化 | `superseded/complete` |

时间片让出不是失败或 BullMQ retry。当前 Job 在成功完成一次 `yieldSlice()` CAS 后正常返回 `yielded`；下一物理 Job 由 DB-first outbox 创建。只有基础设施异常才使用同一 Job 的 BullMQ `attempts/backoff`。

## 7. 完整数据流

### 7.1 批量提交 100 个空间

`POST /api/llm-wiki/admin/compile-spaces`：

1. 对 `spaceIds` 去重。
2. DTO 限制最多 100 个 UUID。
3. 一次数据库请求校验这些空间属于当前 workspace。
4. 为每个没有活动 Run 的空间创建一个 `queued/text` Run。
5. 如果存在 `queued/text AND initialized_at IS NULL` 的尚未开始 Run，则合并请求并返回原 Run。
6. 如果存在已经开始的活动 Run——包括 `initialized_at IS NOT NULL` 且正在等待 continuation 的 queued Run——则设置其 `rerun_requested=true`，不创建并行 Run。
7. 数据库事务提交后调用一次 `dispatchPending()`；调用失败不影响 API 接受结果，5 秒恢复任务会再次投递。

这三个分支必须替换当前 `createRun()` 中“查出全部非终态 Run 后无条件 supersede”的代码，不能在旧 supersede 循环之后再补 coalesce 判断。普通 request 在空间行锁内只读取唯一活动 Run 并按 `initialized_at` 分流；`superseded` 只保留给显式 `forceResetAndCreateRun()`、generation reset 和管理性替换。

API 返回建议改为：

```ts
type CompileSpacesResponse = {
  requestedSpaceCount: number;
  acceptedRunCount: number;
  coalescedRunCount: number;
  rerunRequestedCount: number;
  runs: Array<{
    spaceId: string;
    runId: string;
    disposition: 'created' | 'coalesced' | 'rerun_requested';
  }>;
};
```

Redis 不参与创建 Run 的数据库事务，避免 DB/Redis 双写原子性问题。

`requestRuns()` 不再执行 reuse planning，因此 API 不同步返回“本次无事可做”。即使空间最终全量复用，首次响应也为 `created`，Run 会先短暂出现在 `queued/text`，随后由 Worker claim、初始化并通过 `finishRun()` 直接进入 `succeeded/complete`。`CompileSpacesResponse.disposition` 不增加瞬时 `completed` 分支；Diagnostics 的“排队空间”允许出现这种短尖峰，并另行展示 `initialized_at IS NULL` 的“等待初始化”数量，不能把它解释成实际仍有页面待编译。

### 7.2 空间文字阶段

Outbox 从数据库查询 `queued/text` Run，并投递：

```text
jobName = KNOWLEDGE_COMPILE_SPACE_TEXT
jobId   = knowledge-space-text__{runId}__text__{spaceJobSequence}
priority = 5
attempts = 3
```

`spaceJobSequence` 由数据库预留事务单调递增。首次时间片为 1；每次正常让出后，下一个 continuation 使用新 sequence，因此不会尝试复用 BullMQ 中已经 completed 的 Job ID。

时间片预算按 Worker activation 计算。相同 sequence 的 BullMQ retry/stalled 接管会重置本次 activation 的页数和单调时钟，因为前一次异常已经释放空间槽；已提交 RunPage checkpoint 不重置。`spaceJobSequence` 表示正常 continuation 代次，不表示 BullMQ attempt。

Job payload 只携带身份，不携带页面正文：

```ts
interface IKnowledgeCompileSpaceTextJob {
  workspaceId: string;
  spaceId: string;
  spaceRunId: string;
  knowledgeGeneration: number;
  spaceJobSequence: number;
}
```

Worker 流程：

1. 使用 `runId + phase + spaceJobSequence + spaceJobId` 原子 claim Run，并写入新的 `execution_token`、`worker_id`、`heartbeat_at`。首次 activation 接受 exact `queued` reservation；同 Job retry/stalled 接管可以在 exact sequence/jobId 仍匹配时从 `compiling` 重新 claim 并替换旧 token。任一成功 claim 同时清零 `space_job_recovery_count`。
2. 如果 Run 尚未初始化，导出空间快照、catalog snapshot、reuse candidates，读取排除当前 Run 后的最近真实完成 Run，处理 removed-source 清理并补齐 RunPages；初始化 CAS 最多成功一次。
3. 在每个页面开始前重新校验 Run phase、generation 和本次 `execution_token`。
4. 按稳定顺序读取文字状态未终结的 RunPages，每次只编译一个页面。
5. 页面编译、校验和 publication 在既有事务边界内完成；每次 LLM/provider 调用返回后、publication 前再次校验 `execution_token`。
6. 页面完成后更新 RunPage 和 Run 计数，并刷新 heartbeat。
7. 每个到达文字终态的页面都计入当前时间片页数，包括 `succeeded`、`failed` 和 `skipped`。
8. 页面 checkpoint 后检查预算：处理页数达到 5，或单调时钟耗时达到 5 分钟，且仍有未终结文字页面时，调用 `yieldSlice()`。
9. `yieldSlice()` 使用 execution token CAS 将 Run 从 `compiling/text` 改回 `queued/text`，清空 `space_job_id`、dispatch ack、worker 和 execution token，将 `space_job_queued_at/last_yield_at` 设为当前时间并记录 reason，然后当前 Job 正常返回。
10. 页面业务失败记录后继续下一页；基础设施失败抛出，让当前物理 Job 按 BullMQ attempts 重试，不创建 continuation。
11. 文字屏障完成后执行 initial aggregate，进入 `images`，或由当前 lease 调用 `finishRun()` 完成。

稳定页面顺序建议：

```text
run_page.created_at ASC, run_page.source_page_id ASC
```

时间预算是页面安全边界上的软预算，不会取消已经开始的页面。等待一个空间槽释放的工程上界为：

```text
SPACE_SLICE_MAX_MS
+ KNOWLEDGE_PAGE_DEADLINE_MS
+ KNOWLEDGE_AGGREGATE_DEADLINE_MS
+ outbox 调度间隔
```

默认值下是 `300000 + 900000 + 300000 + 5000 = 1505000ms`，即约 25 分 5 秒。aggregate 只会发生在页面屏障后，但为了给出真正的单槽最坏上界，公式按“时间片已接近 5 分钟、最后一页用满 15 分钟、再执行 5 分钟 aggregate”串行累加。这是极端失败上界，不是 P99 目标。一个页面开始时创建总 deadline `AbortSignal`，并向 exporter/database、compiler provider、materializer、embedding 和 publication 前 fence 传递；超时标记当前 RunPage `page_timeout`，然后在 checkpoint 让出。不得用一个留下后台未取消 Promise 的简单 `Promise.race()` 伪造超时；各 adapter 必须支持原生取消或下游硬超时，publication 仍必须重新校验 lease。

第一版同时固定以下复杂度上限，避免“有 deadline 但在 deadline 内无限发起请求”：

```text
单页 compiler 输出 artifact 最多 20
单页需 LLM materialization 的 canonical artifact 最多 8
单页发布 chunk 最多 200
embedding 每批最多 50，批并发最多 2，单请求超时 30s
PostgreSQL statement timeout 30s
compiler 单次请求继续受 KNOWLEDGE_COMPILER_TIMEOUT_MS 限制
```

`DATABASE_STATEMENT_TIMEOUT_MS` 只是在线应用连接的默认上界，不能让 schema migration 继承 30 秒限制。迁移执行器必须使用独立的 migration statement timeout，或在其自身事务内显式 `SET LOCAL statement_timeout` 为更高的运维值；禁止为了跑迁移而取消在线 Worker/HTTP 的 SQL 上界。

超出 artifact/materialization/chunk 上限时在任何 canonical publication 前以 `page_complexity_limit` 终结该页，不截断后静默发布不完整知识。`KnowledgeArtifactMaterializerService` 不再允许 artifact 数量决定无常量上限的 LLM 调用次数。`ReviewService.generateText()` 也要补硬超时，但 Review 留在独立的旧文字维护队列，不计入空间槽等待上界。

复杂度上限只限制请求数量，不保证最坏调用时长一定落在页面 deadline 内。例如 8 次 materialization 每次最多两次 120 秒 provider 请求，理论上可超过 15 分钟；这时 `page_timeout` 是预期的预算终态，不是 deadline 失效。Diagnostics 必须把 `page_timeout` 单独归类为“预算超时”，与 provider 永久错误、publication 错误和基础设施失败分开统计；真实 provider P99 决定 15 分钟是否需要后续校准。

一个时间片 Job 不持有跨页面数据库事务。Worker 崩溃或当前 Job 重试时只查询未终结页面；正常 continuation 也从相同 RunPage checkpoint 继续，不重新初始化 Run。

### 7.3 页面图片提取

图片的逻辑屏障仍然是 RunPage，但 BullMQ 物理任务改为单图：

```text
jobName = KNOWLEDGE_COMPILE_IMAGE
jobId   = knowledge-image__{runId}__{pageId}__{sha256(attachmentId|attachmentVersion|sourceContentHash)}__{generation}
attempts = 3
```

Job payload 只携带一张图的身份：

```ts
interface IKnowledgeCompileImageJob {
  workspaceId: string;
  spaceId: string;
  spaceRunId: string;
  runImageId: string;
  knowledgeGeneration: number;
}
```

Redis payload 只携带 RunImage 身份；Worker 必须从 PostgreSQL 读取冻结的 source/attachment identity 和图片元数据，不从 Job payload 信任正文或图片属性。

继续保留现有“每页最多理解 50 张图”的业务安全限制。Run 初始化只为冻结 snapshot 中按 `image_ordinal` 的前 50 张创建 RunImage，超出部分直接累计到父 RunPage `skipped_image_count`；不是通过创建更多 Job 绕过安全限制。RunPage `expected_image_count` 仍记录原始总数，因此 counters 始终可对账。

初始化必须区分两类页面：

- 非复用页：前 50 张每张都写 RunImage。已命中 ready extraction 的子行直接以 `succeeded + extraction_id` 落库，其余为 `pending`；父 RunPage 的 succeeded 初值等于 succeeded 子行数，skipped 初值等于超出 50 张的数量。不得先在父行预填 ready 计数、却不写对应子行。
- 整页 reusable：保留现有 `image_status='succeeded'` / `merge_status='succeeded'` 和父行计数，不创建 RunImage，不进入图片 dispatcher，也不允许任何子行聚合查询重算该父行。

因此子行聚合不是“扫描所有 RunPage 并覆写”，而是某个 RunImage 终态 CAS 成功后，只在同一事务重算它所属、且原本非终态的 RunPage。这使非复用页满足“`expected = 子行终态 + 超限 skipped + 子行非终态`”，同时不破坏无子行的整页复用语义。

单图 payload 不再重复 source snapshot；Worker 通过 RunImage 关联的 RunPage 读取它。业务层的 `sourceVersion/sourceContentHash` 仍必须使用以下映射，任何 raw SQL 都只能引用右侧物理列名：

```text
snapshot.sourceVersion
  == RunPage.expectedSourceVersion       // Kysely property
  == expected_source_version             // PostgreSQL column

snapshot.sourceContentHash
  == RunPage.expectedSourceContentHash   // Kysely property
  == expected_source_content_hash        // PostgreSQL column
```

`attachment.updatedAt.toISOString()` 只保留毫秒，PostgreSQL `timestamptz` 可保留微秒。RunImage `expected_attachment_version` 继续使用 `timestamptz`，但写入时必须规范到毫秒，与 `attachments.updated_at` 或 extraction 比较时必须沿用现有规则：

```sql
date_trunc('milliseconds', expected_attachment_version)
  = date_trunc('milliseconds', attachments.updated_at)
```

禁止在 SQL 中直接比较两个未截断的 `timestamptz`，也禁止一处用 ISO 字符串、另一处用微秒时间戳。

图片 Worker：

1. 以 `runImageId + jobId + generation` CAS 读取 RunImage 冻结快照，并校验 Run、RunPage、phase 和 source/attachment identity。
2. 读取 `knowledge_image_extractions`，优先复用 ready cache。
3. 最多执行一次 storage read、一次本地 normalization 和一次 VLM 调用。
4. storage read 硬超时 30 秒，VLM 继续受 `KNOWLEDGE_IMAGE_TIMEOUT_MS` 限制，整个 activation 受 `KNOWLEDGE_IMAGE_JOB_DEADLINE_MS=180000` 限制。storage adapter 必须传递原生 AbortSignal：S3/Azure 取消 SDK 请求，local driver 取消 `readFile`。
5. OCR/caption 和 fingerprint 保存到 PostgreSQL，再于同一事务终结 RunImage 并重算父 RunPage counters/status。
6. 不同图片、页面和空间由共享队列并行处理。
7. 不直接写 Wiki、chunk、link、graph 或 canonical artifact，也不向空间 Job 返回 OCR/caption 大对象。

现有 `formatImageKnowledge()` 是页面级、按图片顺序消耗共享 40k 字符预算的操作，不能拆到单图 Worker。这不阻碍单图调度：单图 Worker 只保证 extraction 和 RunImage 结果落库；image-merge Runner 重新导出并验证页面 snapshot 后，以 RunImage 按 `image_ordinal` 排序重建“冻结的前 50 张” source images，再通过 `readReadySource() -> formatImageKnowledge()` 从 DB extraction 重建增强正文。禁止将当前导出中超出 RunImage 账本的第 51+ 张缓存图重新带回 merge，否则会破坏超限 skipped 语义。旧 `enrichSource()` 的页面级收尾不进入单图 Job。

图片的单次 active 占槽默认硬上界为 3 分钟。BullMQ 的 3 次 attempts 会增加某张图的总完成时间，但 backoff/waiting 不占用图片 Worker 槽；这与当前一个页面 Job 最坏串行 50 次 `120s` 调用有本质区别。

### 7.4 图片队列公平与有界投递

不能在一个空间进入 `images` 时把它的几千个页面全部放入 Redis。继续复用数据库状态作为 outbox 和 outstanding 的权威镜像，并将查询改为按 Run 公平补充。

第一版固定规则：

```text
IMAGE_MAX_OUTSTANDING_PER_RUN = 5
IMAGE_DISPATCH_BATCH_SIZE = 100
IMAGE_REDIS_RECOVERY_MAX = 3
```

含义：

- 一个 Run 在 `knowledge_space_compile_run_images` 中 `status IN ('queued', 'processing')` 的单图行最多 5 个；这两个状态之和是逻辑 outstanding，不能通过查询 Redis 计算。
- 每个调度周期从多个 Run 补足空位，单批最多投递 100 张图。
- 一张图终结后，同 Run 的下一个 pending RunImage 才会被补入。
- 这不是系统并发上限，只是防止单个大空间淹没共享图片队列。

图片 dispatcher 只读取初始化时已冻结的 RunImage/RunPage，不再调用 `exportPageSources()`，不根据实时 `source.images.length` 改写 expected counters。它使用“数据库先预留，Redis 后投递”的流程：

```text
短数据库事务（逐个候选 Run）
  -> SELECT Run FOR UPDATE SKIP LOCKED
  -> count(RunImage.status IN ('queued', 'processing'))
  -> slots = 5 - outstanding
  -> SELECT 最老 pending RunImages FOR UPDATE SKIP LOCKED LIMIT slots
  -> CAS pending -> queued，写入确定性 job_id，清空 dispatched_at
  -> commit

事务提交后
  -> queue.add(job_id)
  -> best-effort CAS 写 dispatched_at
```

候选 Run 查询使用 PostgreSQL window function 按 `run_id` 分区，并按 Run 的 `queued_at` 交错排序；不要先把所有 pending 行加载到 Node.js。多个实例同时 dispatch 时，对 Run 行的短锁保证它们不会基于同一个旧 outstanding 数重复预留，因此数据库不变量 `RunImage queued + processing <= 5` 始终成立。

数据库和 Redis 不存在普通事务下的跨系统原子提交。若数据库已置 `queued` 而 `queue.add()` 失败，RunImage 保持 `queued` 且 `dispatched_at IS NULL`；5 秒 reconciler 必须分批查询这些从未确认投递的行，并用同一确定性 Job ID 反复执行 `queue.add()`。BullMQ 已存在相同 ID 时按幂等结果处理，然后补写 ack 时间；这类“首次投递未成功”不增加 Redis recovery count。

另设低频恢复扫描处理 ack 已写但长时间仍为 `queued` 的行。它不盲目 `queue.add()`，而是先查保留的 exact Job：仍 waiting/delayed/prioritized/active 则不动，final failed/异常 completed 则终结 RunImage，missing 则通过 CAS 清空 ack、递增 `redis_recovery_count` 后再由快速 reconciler 重投；达到 3 次时不再重投而是终结 failed。禁止采用“先 `queue.add()`、成功后再置 queued”的顺序。

图片 Worker 只允许通过 CAS 将预留的 RunImage `queued -> processing`，同时写入 `processing_expires_at = now() + 210s`、递增 attempt 并将该行 `redis_recovery_count` 清零。完成时在同一数据库事务中将其置为 `succeeded|failed|skipped`；`failed` 必须同时写入 `failure_class='retryable_exhausted'|'permanent'`，不能从 attempt_count 猜测。然后只重算该子行所属的非终态 RunPage；终态提交即释放一个逻辑 slot。同一 Job 的 BullMQ retry 保留 RunImage `processing` 与原 jobId，新 activation 通过 exact identity CAS 接管并刷新 expiry；不创建无身份的第二个 Job。

父 RunPage 的推导规则是持久化状态的纯函数，不依赖 Worker 进程内的 `retryableFailureCount`：

```text
仍有 processing 子行                                      -> image_status=processing
否则仍有 queued 子行                                  -> image_status=queued
否则仍有 pending 子行                                 -> image_status=pending
否则存在 failed/failure_class=retryable_exhausted             -> image_status=failed
否则 failed 或 skipped_image_count > 0                           -> image_status=partial
否则                                                        -> image_status=succeeded

图片已全部终态且 succeeded_image_count > 0                -> merge_status=pending
图片已全部终态且 succeeded_image_count = 0                -> merge_status=skipped
```

非复用页初始化和每次子行终结都调用同一个推导函数；图片尚未全部终态时 `merge_status=waiting_images`。这与现有页面 Job 语义等价：最终仍有 retryable failure 时整页图片状态为 failed；只有永久失败/skipped 时为 partial；只要存在成功 extraction，merge 仍必须进入 pending。

### 7.5 图片完成屏障

每个单图 Job 结束时，在终结 RunImage、重算 RunPage 的同一个事务中检查该 Run：

```text
是否仍存在 RunImage.status IN ('pending', 'queued', 'processing')
或具有 RunImage 子行的 RunPage.image_status IN ('pending', 'queued', 'processing')
```

最后一个 RunImage 终结时：

- 无论是否存在可用图片结果，都将 Run 原子转换为 `queued/image_merge`。
- 多个图片 Worker 同时完成时，只有一个事务能成功推进 phase。

图片 Worker 不持有空间 execution lease，因此禁止从图片完成事务直接把 Run 写成 `succeeded/partial/failed`。没有 ready merge 页时，image-merge Runner 取得空间 lease 后跳过页面循环，直接执行有界 final aggregate 并通过唯一 `finishRun()` 终态化；这会多一个很短的空间 Job，但保持终态和 follow-up 只有一个正确入口。

推进到 `queued/image_merge` 的事务只设置 phase/status、`space_job_queued_at=now()` 并清空空间 Job reservation/ack；不直接递增 sequence 或调用 Redis。后续 outbox reservation 负责生成首个 image-merge sequence 和 Job ID。

推进后由 outbox 投递该 Run 的首个空间合并时间片；后续 continuation 由时间片 yield 触发，但任一时刻只有一个 DB 有效 reservation：

```text
jobName = KNOWLEDGE_MERGE_SPACE_IMAGES
jobId   = knowledge-space-image-merge__{runId}__image_merge__{spaceJobSequence}
priority = 1
attempts = 3
```

`priority=1` 高于文字时间片的 `priority=5`，但 BullMQ priority 只影响 waiting/prioritized 集合中“下一个 Job”的选择，不抢占任何 active Job。可控等待由空间时间片提供：所有 active 文字时间片都会在页面安全边界达到 5 页或 5 分钟后让出；第一个空间槽释放时，等待中的 image merge 会优先于文字 continuation 和尚未开始的文字 Run 获取槽位。

同优先级遵循 BullMQ 的入队顺序。文字 continuation 是新 Job，会排在已经等待的同优先级文字 Job 后面，使 100 个空间逐批获得执行机会；image merge continuation 同理在 priority=1 内公平排队。若所有槽都正在执行页面，等待时间仍需加上当前页面剩余执行时间，不宣称 priority 可以即时抢占。

### 7.6 空间图片知识合并

`KNOWLEDGE_MERGE_SPACE_IMAGES` 的每个时间片获取一个空间槽后：

1. 使用 `runId + image_merge + spaceJobSequence + spaceJobId` claim `queued/image_merge` Run，生成新的 execution token。
2. 查询 `merge_status` 未终结且有 ready extraction 的 RunPages。
3. 按稳定页面顺序逐页执行。
4. 重新导出页面并验证 source/attachment snapshot。
5. 只按 RunImage `image_ordinal` 读取该 Run 冻结的前 50 张 ready OCR/caption，用冻结 metadata 调用 `readReadySource()/formatImageKnowledge()`；不把超限 skipped 图重新带入。
6. 计算 `effectiveKnowledgeHash`。
7. 使用“页面文字 + 图片知识”重新编译该页面。
8. 在 publication transaction 内写 artifacts、contributions、chunks、links、graph 和 RunPage merge 状态。
9. 每个 merge 页面 checkpoint 后使用与文字阶段相同的 5 页/5 分钟预算；仍有页面时执行 `compiling/image_merge -> queued/image_merge` 的 token CAS，让出槽位并由 outbox 投递新 sequence continuation。
10. 所有页面到达 merge 终态后执行 final aggregate。
11. 由当前 lease 调用唯一 `finishRun()`，将 Run 终结为 `succeeded|partial|failed` 并把 phase 设为 `complete`。

同一个空间合并页面并发固定为 1；跨时间片也必须等前一 execution token 完成 yield CAS 后才能 claim。不同空间的 `merge-space-images` 可以由不同空间槽并行执行。

当前 `KNOWLEDGE_MERGE_PAGE_IMAGES` 的核心业务逻辑应先通过 characterization tests 抽取为可被空间 Runner 调用的 service；最终版本删除逐页 merge Job 的生产和消费路径，只保留新空间 merge Runner。

## 8. 一致性和可靠性约束

### 8.1 单活动 Run

保留现有部分唯一索引：

```text
UNIQUE(workspace_id, space_id)
WHERE status IN ('queued', 'compiling', 'aggregate_pending', 'aggregating')
```

同一空间不能通过增加实例获得空间内并行；增加实例只增加不同空间之间的并行。

### 8.2 canonical artifact 空间作用域

空间之间可以完全并行的前提是 artifact 不存在跨空间共同所有权。当前代码已经满足这个前提，并将它提升为目标架构必须保持的不变量：

```text
canonical artifact ownership scope = (workspaceId, spaceId)
stable artifact ID input            = workspaceId + spaceId + kind + canonicalKey
canonical unique key                = workspaceId + spaceId + pageType + canonicalKey
```

编译任务只能读取和修改自身 `(workspaceId, spaceId)` 下的 artifact、contribution、chunk、link 和 graph；validator 必须拒绝 artifact scope 与编译 scope 不一致。跨空间链接只是指向另一个空间资源的引用，不表示双方共享同一个 canonical artifact，也不能让当前空间任务写入目标空间。

如果未来引入 workspace/global 级共享 canonical artifact，本方案“不同空间可完全并行”的一致性证明将不再成立。届时必须把共享 artifact 拆成独立所有权域，并增加该域级别的串行化或 contribution revision/optimistic fence；不能直接复用本方案的空间锁和空间执行槽。

### 8.3 现有空间行锁与 contribution 物化临界区

当前 Run-scoped publication guard 已经在事务内锁定 `spaces` 行。该锁应继续保留，因为它负责 generation、active Run、phase 和 source snapshot 的权威发布校验，并串行化最终事务写入。

但它不是 contribution materialization 的完整串行保证：

```text
当前页面 Job P1                       当前页面 Job P2
读取旧 contributions                 读取旧 contributions
LLM 生成 M1                          LLM 生成 M2
构建待发布 artifact                  构建待发布 artifact
        │                                    │
        ├─ 获取 spaces FOR UPDATE            │ 等待行锁
        ├─ 写 contribution + M1               │
        └─ commit                             │
                                             ├─ 获取行锁
                                             ├─ 不重读 contribution
                                             ├─ 写 contribution + 陈旧 M2
                                             └─ commit
```

目标架构的第一版不把 LLM 调用移动到数据库事务中，也不增加另一把空间锁。LLM 合并可能耗时很长，放入事务会长期占有行锁并扩大数据库故障面。

第一版通过结构性不变量消除竞态：

```text
同一 Run 同一时刻只有一个可 claim 的 space_job_sequence
+ 每个时间片 Job 内页面使用顺序循环
+ continuation 只能在前一时间片完成 yield token CAS 后创建
+ text 与 image_merge phase 不重叠
= 同一空间不会同时执行两条 contribution materialization 链路
```

这意味着无论两个页面位于同一时间片还是相邻 continuation，第二个页面开始读取 contribution 时，第一个页面的 publication transaction 已经提交。共享 `KNOWLEDGE_SPACE_QUEUE` 和 BullMQ priority 本身都不提供按空间串行；真正的保证来自“单活动 Run + 单有效 sequence + execution-token/yield CAS + 时间片内顺序循环 + phase CAS”。

如果未来重新引入同空间页面并发，必须增加 contribution revision/optimistic fence，并在版本冲突时重新读取和重新物化；仅依赖现有 `spaces FOR UPDATE` 不足以保证 canonical artifact 正确。

#### 8.3.1 全局多表锁顺序

新流程所有同时锁定多个编译实体的事务，必须遵守唯一顺序：

```text
spaces -> knowledge_space_compile_runs
       -> knowledge_space_compile_run_pages
       -> knowledge_space_compile_run_images
```

事务可以从该序列的中间开始，但一旦锁定了后面的实体，禁止再请求前面的锁。不得用一条三表 join 的无 `OF` `SELECT ... FOR UPDATE` 来声称锁顺序；PostgreSQL 执行计划可以改变访问顺序。需要多层锁时必须分步显式锁定。

现有 `markPageMergeQueued()` 的 RunPage/Run/Space join `FOR UPDATE` 与目标 `finishRun()` 的 `spaces -> Run` 存在反序死锁可能。虽然该旧方法最终会删除，Task 2C 在引入 `finishRun()` 的同一个 commit 就必须先将它改为 `spaces -> Run -> RunPage` 显式锁序，不得把死锁窗口留到 Task 8。Task 6 改造图片完成屏障时也必须从 Run 开始，再锁 RunPage/RunImage，不保留“先更新页、再更新 Run”的新反序路径。

### 8.4 execution token 与长任务接管

单个空间时间片通常执行数分钟；在页面接近超时、网络分区或 stalled 重分配时，旧 Worker 仍可能短暂继续运行。

每次空间 Job activation 生成随机 `execution_token`：

```text
Run.execution_token = current activation token
```

每次页面 publication guard 除现有条件外，必须验证：

```text
runId
knowledgeGeneration
allowed phase
spaceJobSequence
pageInput.sourceVersion == RunPage.expectedSourceVersion
pageInput.sourceContentHash == RunPage.expectedSourceContentHash
executionToken
```

其中 Kysely 的 `expectedSourceVersion/expectedSourceContentHash` 分别映射 PostgreSQL `expected_source_version/expected_source_content_hash`；不要在 SQL 中使用 `source_version` 或 `source_content_hash`。

`execution_token` 只属于当前空间时间片的执行租约，不能机械添加到所有 Run/RunPage 写方法。新增独立的 `KnowledgeSpaceExecutionRepo`，所有由空间 Runner 发起的写入都必须接收完整 lease：

```ts
interface SpaceExecutionLease {
  runId: string;
  knowledgeGeneration: number;
  jobPhase: 'text' | 'image_merge';
  spaceJobSequence: number;
  spaceJobId: string;
  executionToken: string;
}
```

`jobPhase` 是物理时间片身份，在一次 activation 内不变；Run 的业务 `phase` 可以在同一时间片中从 `text -> initial_aggregate` 或 `image_merge -> final_aggregate`。CAS 必须使用固定映射：

```text
jobPhase=text        允许 run.phase IN ('text','initial_aggregate')
jobPhase=image_merge 允许 run.phase IN ('image_merge','final_aggregate')
```

不得因为 aggregate 改变了 Run phase 就丢失当前 lease，也不得新建一个未经调度的 execution token。

以下空间执行方法必须在同一 SQL/事务中校验完整 lease，不能只在 service 层预查：

```text
claimSpaceSlice
claimRecoveryLease
initializeRun
heartbeatSpaceSlice
completeTextPage
completeMergePagePublication
failMergePage
yieldSpaceSlice
requeueMissingSpaceSlice
completeInitialAggregate
finishRun
```

写入边界固定为：

| 写入者 | 必须使用的 fence |
|---|---|
| 空间文字/merge Runner | 完整 `SpaceExecutionLease` CAS |
| 图片 dispatcher/Worker | run generation + phase + source/attachment snapshot + RunImage status/jobId CAS |
| 空间/图片 outbox reservation 与 dispatch ack | queued 状态 + phase + 确定性 jobId/sequence CAS |
| compile request / force reset | `spaces FOR UPDATE` + generation + 单活动 Run 唯一索引 |

RunImage reservation/claim/complete、dispatch ack 和 force reset 的调用者不持有空间执行租约，因此不得为了形式统一强制传 `execution_token`。它们必须使用右侧身份和状态 CAS；否则会把图片异步阶段错误耦合到一个已经释放的空间槽。

新 Worker 接管时会替换 token，旧 Worker 后续 publication 和进度写入自动变成 no-op。这是空间长任务可靠接管的必要 fencing，不依赖进程内锁。Runner 在每页开始前以及每次 LLM/provider 调用返回后都要检查 token；发现失效立即退出。`heartbeat_at/execution_lease_expires_at` 由定时 heartbeat 和 checkpoint 双重刷新，但不能代替 BullMQ lock renewal。

### 8.5 确定性 Job ID 和 DB-first outbox

空间 Job ID 由 `runId + phase + spaceJobSequence` 决定；单图 Job 由 Run/page/attachment/source snapshot/generation 决定。两类 Job 都统一使用“DB-first reservation + Redis idempotent delivery”：

```text
短数据库事务
  -> 锁定/CAS 待投递记录
  -> 写入确定性 jobId，将记录置为 reserved/queued，并清空 dispatched_at
  -> commit

事务提交后
  -> queue.add(deterministicJobId)
  -> best-effort CAS 写 dispatched_at
```

任何一步崩溃都能恢复：

- DB commit 前崩溃：事务回滚，记录仍 pending，下次重新预留。
- DB commit 后、`queue.add()` 前或过程中崩溃：记录已经保留确定性 jobId 且 `dispatched_at IS NULL`，reconciler 再次添加同一 Job。
- `queue.add()` 成功但调用方未收到响应或 DB ack 失败：reconciler 重复添加同一 jobId，BullMQ 幂等返回已有 Job，然后补写 ack。
- Worker 崩溃：BullMQ stalled/retry；空间 Worker 从 RunPages checkpoint 恢复，图片 Worker 从 RunImage 镜像状态恢复。

不把 `queue.add()` 包装成数据库事务的一部分，也不存在真正的 DB↔Redis 原子提交。可靠性来自数据库先记录投递意图、确定性 Job ID 和周期性 reconciler。进程内 `dispatching` 标志只防止单实例重入，不能作为跨实例互斥或 outstanding 计数依据。

空间 continuation 的预留事务必须锁定 Run，确认 `status='queued'`、phase 未变化且 `space_job_id IS NULL`，再执行 `space_job_sequence = space_job_sequence + 1` 并根据返回值生成 Job ID。同一个 sequence 的 Redis 重投复用同一 ID；正常时间片让出后的新 continuation 必须使用新 sequence，不能复用已经 completed 的 Job ID。

空间 outbox 的候选顺序固定为：先按 phase 映射内部 priority（`image_merge=1`、`text=5`），再按 `space_job_queued_at ASC, run_id ASC`。这样 Redis 恢复或 dispatcher 分批运行时，较新的 text continuation 也不会在 DB 投递层越过已经等待的同优先级首次时间片；BullMQ 再按 priority/入队计数选择下一个 Job。

reconciler 有两层：每 5 秒快速扫描 `dispatched_at IS NULL` 的 queued 记录，直接幂等添加相同 ID 并补 ack；这是首次投递未确认，不计 Redis recovery count。另以较低频率扫描 ack 已写但超过阈值仍未被 claim 的 queued 记录，在事务外查 exact Job 后分流：仍可执行/重试则不动，final failed/异常 completed 进入有 fence 的失败收敛，missing 则 CAS 清 ack、递增 recovery count 后再由快速层重投同一 ID。恢复耗尽后不得无限 `queue.add()`：空间 Run 通过 exact queued reservation 取得 recovery lease 后调用 `finishRun()`，RunImage 以 exact status/jobId/generation CAS 终结并推进屏障。Redis 查询失败时不做破坏性转换。

### 8.6 最终失败与孤儿 Run 回收

BullMQ 重试与 DB execution lease 是两个独立系统。不能假设 `failed` 事件一定到达，也不能只凭 lease expiry 就猜测执行者已死：页面允许运行 15 分钟，而 DB lease TTL 是 3 分钟，连接池压力可能让健康 Worker 的 heartbeat 暂时无法落库。

空间 Job 有两条收敛路径：

1. 空间 Processor 收到“attempts 已耗尽”的 `failed` 事件时，使用 exact `(runId, jobPhase, spaceJobSequence, spaceJobId)` 调用 `claimRecoveryLease()`。该方法按 `spaces -> Run` 加锁、替换旧 token，再通过唯一 `finishRun(recoveryLease, 'failed')` 终态化。
2. 每 30 秒扫描非终态且 `execution_lease_expires_at < now()` 的 Run，但先在事务外查询 exact BullMQ jobId，再使用原 identity + expiry 的 CAS 重新校验并落库：

```text
failed                                      -> claimRecoveryLease + finishRun(failed)
completed 但 DB 仍非终态                     -> claimRecoveryLease + finishRun(failed)
active/waiting/delayed/prioritized/
waiting-children                            -> 不动，交给 BullMQ retry/stalled
missing 且 space_job_recovery_count < 3    -> claimRecoveryLease
                                               + requeueMissingSpaceSlice()
                                               + 由 outbox 创建新 sequence
missing 且已恢复 3 次                     -> claimRecoveryLease + finishRun(failed)
Redis 查询失败                              -> 本轮不做破坏性状态转换
```

`requeueMissingSpaceSlice()` 是 lease-bound 操作：它使旧 token 失效，将 Run 改回同 phase 的 queued，清空当前 reservation/dispatch ack/worker/lease，递增 `space_job_recovery_count`；下一次成功 claim 才将 recovery count 清零。这是对 Redis Job 异常消失的有界交通层恢复，不是第二个终态入口。

reaper 不得持有数据库锁调用 Redis，也不得拥有“无 lease 直接 update terminal status”的后门。它的特权只是在 exact identity 仍匹配、lease 仍过期或 exact Job 已永久失败时原子创建 recovery lease；终态、`rerun_requested` 和 follow-up 仍只能由 `finishRun()` 处理。

从未成功写入 dispatch ack 的 queued Run 不由 lease reaper 处理，只由空间 outbox 快速 reconciler 幂等投递；已经 ack 但未 claim 的 queued Run 则由低频 reconciler 查询 exact Job，只有 final failed、异常 completed 或 missing 才进入 fenced recovery。单图 Job 采用同样的状态判定：failed event 以 `(runImageId, jobId, generation)` CAS 终结 RunImage；事件丢失时，reaper 先找 `processing_expires_at` 过期行，在事务外查 exact Job，再以 identity/status/expiry CAS 分流。final failed 或“completed 但 DB 仍 processing”终结为 failed；仍可执行/重试的 Job 不动；missing 时只在 `redis_recovery_count < 3` 时改回 queued、清空 dispatch ack 并递增 count，达到 3 次则以 `redis_job_missing_exhausted` 终结。快速 outbox 对“从未成功 ack”的首次投递可持续重试；只有曾经 ack/processing 后又 missing 的恢复才计入 3 次上限。Redis 不可用时本轮不做破坏性状态转换。

两类 reaper 操作都必须幂等，并暴露 `recovered_as_failed|redis_job_missing|redis_redelivery_exhausted|completed_without_db_terminal`。BullMQ Job 状态只是“是否安全恢复”的信号，Run/RunPage/RunImage 仍是业务事实来源。

### 8.7 页面失败规则

| 失败类型 | 处理 |
|---|---|
| 页面内容不支持、永久校验失败 | 标记该 RunPage failed，继续下一页 |
| 单次 LLM 超时/限流 | 页面内有界重试；仍失败时空间 Job 抛出或记录 retryable |
| 数据库/Redis/存储短暂不可用 | 让空间 Job 失败，由 BullMQ 重试 |
| source 在编译中变化 | 当前页面 no-op/skipped，设置 rerunRequested |
| generation 或 Run 被替换 | publication fence 拒绝，旧 Job 正常结束为 no-op |
| 图片部分失败 | 使用成功图片继续，Run 最终为 partial |
| final aggregate 失败 | 保留已发布页面知识，重试 final aggregate 阶段 |

禁止因为一个永久页面失败而从第一页重跑整个空间。

### 8.8 页面更新、follow-up 与 force rebuild

当前 `page.listener.ts` 在空间存在活动 Run 时直接 `continue`，会丢失后续编译意图。调整为统一请求空间增量 Run：

```text
页面更新
  ├─ 无活动 Run：创建 queued/text Run，使用现有 5 秒 delay/coalesce
  ├─ Run 仍 queued 且未初始化：当前 Run 的未来快照会包含修改，不设置 rerun
  └─ Run 已开始：设置 rerun_requested=true
```

页面变更有两个独立入口，必须共用同一个 `requestIncrementalCompileForPages()` 服务：

- `apps/server/src/database/listeners/page.listener.ts`：REST/数据库事件路径。
- `apps/server/src/collaboration/extensions/persistence.extension.ts` 投递的 `PAGE_CONTENT_UPDATED`：Hocuspocus 持久化路径。

`PAGE_CONTENT_UPDATED` handler 仍先执行 access reindex，然后调用该统一服务；它不再自行 `queueAttempt()` 或投递 `KNOWLEDGE_COMPILE_PAGES`。`page.listener.ts` 也不再保留一套不同的 `hasActiveRun -> continue` 逻辑。这两个入口的同一组输入必须产生相同的 created/coalesced/rerun 结果。

当前 Run 终态化时，在同一事务中检查 `rerun_requested`：

- 先将当前 Run 置为终态，再为该空间创建一个新的 `queued/text` incremental Run，使单活动 Run 唯一索引始终成立。
- follow-up 的 `knowledge_generation` 取锁定后的 `spaces.knowledge_generation`；只在终态 Run 的 generation 仍等于该值且不存在更新的活动 Run 时创建。
- 新 Run 重新 snapshot 全空间，但复用计划会跳过未改变页面。
- 多次页面修改只产生一个后续 Run。

新流程只允许通过 `finishRun(lease, outcome)` 自然终态化 Run。该方法按统一顺序先锁 `spaces`、再锁 Run，校验完整 `SpaceExecutionLease`、当前 generation 和活动状态，然后在同一事务中写终态、清理执行租约并按上述规则创建 follow-up。以下路径都必须调用它，不能直接更新 Run 为终态：

1. final aggregate 成功，结果为 `succeeded` 或 `partial`；
2. final aggregate 在有界重试耗尽后永久失败；
3. `initializeRun()` 发现全量复用、无需页面或 aggregate 工作；
4. 未来新增的任何自然 `failed` 结束路径。

现有 `completeAggregation()`、`failAggregation()` 和 `createRun()` 的直接终态分支在新流程中要么删除，要么改为调用 `finishRun()`；禁止保留第二个能把新 Run 写成 `succeeded/partial/failed` 的 repository 入口。`forceResetAndCreateRun()` 是唯一例外：它在空间行锁事务内把旧 Run 写为 `superseded` 并立即创建替代 force Run，不消费旧 Run 的 `rerun_requested`，也不调用 `finishRun()`。

`rerun_requested` 的语义固定为“当前 Run 完成后再执行一次 incremental”，不继承当前 Run 的 mode：

| 触发场景 | 当前 Run | follow-up mode | follow-up generation | 是否再次清空知识 |
|---|---|---|---|---|
| 普通增量 Run 执行中发生页面更新 | `incremental` | `incremental` | 当前 `spaces.knowledge_generation` | 否 |
| force Run 执行中发生页面更新 | `force_rebuild` | `incremental` | force 已经递增后的同一 generation | 否 |
| 用户再次显式请求 force rebuild | 任意活动 mode | 新 `force_rebuild` Run | 由 reset 流程再递增 1 | 是 |

显式 force 请求不得只设置 `rerun_requested`。它必须继续走 `forceResetAndCreateRun` 语义：使旧 Run superseded、递增 generation、执行一次清理，并创建新的 force Run。旧 Run 后续终态化时若发现 generation 已变化，忽略自己的 `rerun_requested`，不能再创建旧 generation 的 follow-up。

布尔字段足以支持第一版，是因为自动 follow-up 只有 incremental 一种含义。若未来需要合并多个不同 mode/参数的后续请求，应升级为明确的 next-request 记录，不能继续扩展这个布尔值的隐含语义。

这样可以删除常规页面更新直接投递 `KNOWLEDGE_COMPILE_PAGES` 的路径，所有 canonical publication 都经过空间串行边界。

### 9.4 Run 创建与初始化拆分

Repository 增加两个明确操作：

```ts
requestRuns(input): Promise<RequestRunResult[]>
initializeRun(input): Promise<KnowledgeSpaceCompileRun | undefined>
```

`requestRuns()` 只做快速数据库写入，不调用 LLM、Redis、storage 或 source exporter。普通请求必须先锁 `spaces`、再读取唯一活动 Run，并用互斥分支完全替换当前无条件 supersede 循环：

```text
无活动 Run                                      -> 创建 queued/uninitialized Run
queued/text AND initialized_at IS NULL          -> coalesce，返回原 Run
任意 initialized 活动 Run（含 queued continuation） -> rerun_requested=true
```

removed source 不能简单塞进上述第三个分支。当前 `retireRemovedSources()` 同时做 source stale、contribution DELETE 和 orphan artifact stale；目标流程按“立即 fail-closed、延后物理清理”拆成两个职责：

1. 请求控制面或 `PAGE_DELETED/PAGE_SOFT_DELETED` 已知 source IDs 的事件入口，调用同一个 `invalidateRemovedSourcesAndReplan()` 短事务。全空间手动请求没有显式 IDs 时，使用 set-based DB anti-join 比较当前 live pages 与该空间已有 source/contribution IDs；不调用 source exporter。
2. 事务按 `spaces -> Run -> RunPage -> RunImage` 锁序执行，只把 `knowledge_sources` 置 stale 不够，因为检索候选实际过滤 `knowledge_pages/knowledge_chunks.stale_at`，不读取 `knowledge_sources.stale_at`。它必须同时把 removed contribution 触及的全部 canonical artifact、当前 active space overview 及其 chunk/link/graph 子产物置 stale；即使 canonical artifact 仍有其他 contribution，也先暂时隐藏，保证正文和 overview 都不会继续呈现已删除来源。
3. 该事务不删除 contribution、不计算 orphan。若当前 Run 尚未初始化，保留该 Run 并由后续 snapshot 自然排除 removed source；若当前 Run 已初始化，则撤销 execution token、删除该 Run 的冻结 RunPage/RunImage 计划、清空计数/初始化快照和空间 Job reservation，把同一 Run 重置为 `queued/text + initialized_at IS NULL`。`space_job_sequence` 不回退，下一次 reservation 必须生成更大的 sequence/新 Job ID。旧 Worker 在 publication guard 中因 token/phase 不匹配 no-op；若旧 publication 已先取得空间锁，失效事务随后把其结果置 stale。
4. reset/replan 保留 Run 的 id、mode、knowledge generation 和 `rerun_requested`，因此不创建第二个活动 Run，也不把结构删除伪装成 force rebuild；API 随后按 queued/uninitialized 分支返回 `coalesced`。这是一条 source-set correctness 路径，不恢复当前页面进度。
5. `initializeRun()` 基于新的 authoritative source snapshot 再计算 removed IDs、受删除 contribution 影响的 remaining sources，物理删除 contribution 并计算 orphan artifact；受影响但仍有其他来源的 artifact 通过剩余页面的串行 materialization 重新发布，真正 orphan 保持 stale。初始化失败或 Job 永久丢失时 contribution 仍在，但相关产物已经 fail-closed 不可检索。

这样既没有“等待几十分钟初始化期间仍可检索删除内容”的窗口，也不会因为一个从未初始化的 Run 提前做不可恢复的 contribution DELETE。该 replan 必须有并发测试覆盖“旧 Worker 在失效事务前/后到达 publication guard”两种锁序。

`initializeRun()` 由空间 Worker 调用，负责 catalog/snapshot/reuse planning、延后物理 retirement 和 RunPages/RunImages 创建。初始化必须具有 CAS：同一个 plan 最多成功初始化一次；source-set replan 清空 `initialized_at` 后允许产生一个新的 plan 代次，但旧 execution token 永远不能提交旧 plan。

aggregate reuse 查询必须显式接收当前 Run ID，并把资格下推到 SQL：

```ts
findLatestCompletedRunForAggregateReuse({
  workspaceId,
  spaceId,
  excludeRunId: currentRunId,
}): Promise<AggregateReuseRun | undefined>
```

查询至少包含 `run.id != excludeRunId`、`status IN ('succeeded','partial')` 和 `phase='complete'`，再按 `created_at DESC` 取一条；`initializeRun()` 继续校验 compiler/prompt version、generation、catalog hash 和 active overview。不能只依赖调用时序排除自己，也不能让一个更新的 failed/superseded/queued Run 挡住更早但真实完成的复用候选。

Repository 还要提供两个时间片操作：

```ts
reserveNextSpaceSlice(input): Promise<ReservedSpaceSlice | undefined>
yieldSpaceSlice(input): Promise<boolean>
```

`reserveNextSpaceSlice()` 锁定 queued Run，在 `space_job_id IS NULL` 时递增 sequence、生成并持久化 Job ID。`yieldSpaceSlice()` 只接受当前 execution token 和 sequence，在确认阶段仍有未终结页面后，将 Run 改回同 phase 的 queued 状态并清除执行租约；二者都不能调用 Redis。

空间 Runner 的 mutation 从现有大 Repo 中拆到 `KnowledgeSpaceExecutionRepo`，并增加唯一自然终态入口：

```ts
finishRun(
  lease: SpaceExecutionLease,
  outcome: 'succeeded' | 'partial' | 'failed',
): Promise<FinishRunResult | undefined>
```

`KnowledgeSpaceCompilationRepo` 继续负责 request/force、图片状态、outbox reservation 和查询；`KnowledgeSpaceExecutionRepo` 只负责持有空间 lease 时的初始化、页面 checkpoint、heartbeat、yield、aggregate 和终态化。该拆分使 TypeScript 方法签名直接暴露 token 改造清单，避免在 1700 行 Repo 中漏改某个空间 Runner 写入口。

### 10.3 Job options

`KNOWLEDGE_SPACE_QUEUE` 在 `QueueModule` 中统一设置空间 Job 的重试和保留策略：

```ts
const SPACE_QUEUE_DEFAULT_JOB_OPTIONS = {
  attempts: 3,
  backoff: { type: 'exponential', delay: 31_000 },
  removeOnComplete: { count: 1_000 },
  removeOnFail: { count: 1_000 },
};

const IMAGE_QUEUE_DEFAULT_JOB_OPTIONS = {
  removeOnComplete: { age: 3_600, count: 100_000 },
  removeOnFail: { age: 86_400, count: 10_000 },
};
```

不能照抄当前知识队列的 `attempts: 1` 或 `removeOnFail: true`。当前 `KNOWLEDGE_IMAGE_QUEUE` 的 `removeOnComplete: true/removeOnFail: true` 会在 Job 终结时直接删除 hash，使 exact-job reaper 无法区分 completed、failed 和 missing；Task 1 必须在引入 reaper 之前先替换为上述有界保留策略。保留 age 必须显著大于 210 秒 processing expiry + reaper 扫描间隔 + 最大 retry backoff；count 按 100 空间图片压测吞吐验证，超出 count 时仍由 missing 有界恢复兜底。数据库 Run/RunPage/RunImage 终态仍是最终事实源。

空间 Job 只在 `queue.add()` 时补充确定性 ID 和阶段 priority，重试参数从队列默认值继承：

```ts
const SPACE_TEXT_JOB_OPTIONS = {
  priority: 5,
};

const SPACE_IMAGE_MERGE_JOB_OPTIONS = {
  priority: 1,
};

const IMAGE_JOB_OPTIONS = {
  attempts: 3,
  backoff: { type: 'exponential', delay: 31_000 },
};
```

`KNOWLEDGE_IMAGE_QUEUE` 当前队列默认是 `attempts: 1`，但现有 `imageJobOptions()` 已经为图片 Job 显式返回 `attempts: 3`；这是需要保留的现状，不是新增能力。第一版将它收敛为唯一 `IMAGE_JOB_OPTIONS`，并禁止新增不经过该 helper 的图片 `queue.add()`。队列级 retention 与 Job 级 attempts/backoff 是两个独立配置，必须同时存在。

### 10.4 Worker options

Job 的 `attempts/backoff` 不能替代 Worker lock 配置。空间 Processor 在每个实例上声明：

```ts
const SPACE_WORKER_OPTIONS = {
  concurrency: KNOWLEDGE_SPACE_CONCURRENCY,
  lockDuration: 120_000,
  stalledInterval: 30_000,
  maxStalledCount: 2,
  // 不设置 lockRenewTime：BullMQ 使用 lockDuration / 2
};

const IMAGE_WORKER_OPTIONS = {
  concurrency: KNOWLEDGE_IMAGE_CONCURRENCY,
  lockDuration: 120_000,
  stalledInterval: 30_000,
  maxStalledCount: 2,
};
```

这些选项必须传给实际 BullMQ Worker（NestJS `@Processor` 对应的 Worker options），不能只存在于业务 service 配置中。`concurrency` 和 `lockDuration/lockRenewTime` 按 Worker 生效；`stalledInterval/maxStalledCount` 是“per-Worker 声明、同一队列竞争扫描后队列级生效”，同一物理队列的 Worker 必须同值。空间和单图 Processor 都订阅 `stalled`、`lockRenewalFailed` 和 `failed` 事件，并将计数纳入 Diagnostics/告警；事件可能由赢得队列级 stalled 检查的 Worker 发出，不代表该 Worker 原先执行了对应 Job。

Job payload 禁止放入：

- 页面正文；
- catalog snapshot；
- OCR/caption；
- provider response；
- artifact 列表。

这些大对象都由 Worker 按身份从数据库或 exporter 获取。

## 13. 上线边界

当前知识编译能力尚未正式上线，本方案采用一次性启用新架构，不实现运行期迁移状态机：

1. 先在真实部署平台确认 3 实例、同构 Worker 配置和数据库连接预算；不满足 `全部进程 pool 之和 + 保留量 <= max_connections` 时禁止启用 concurrency 10/5。
2. 执行新架构所需的 additive schema migration。
3. 部署唯一的新空间队列、空间 Runner、单图 Worker、reaper 和新生产者。
4. 不启动旧空间编译生产者，不保留旧逐页文字/merge/aggregate handler；保留 `PAGE_CONTENT_UPDATED` 作为维护队列触发入口。
5. 上线后由运维入口对已有空间统一触发 `force_rebuild`，直接使用新架构重新生成知识。

全空间强制编译只是一项上线后的运维操作，不属于空间队列稳态设计。本文不设计旧数据清理脚本、旧 Job 排空、旧 Run 恢复、双协议共存或回滚到旧编译架构。`force_rebuild` 自身继续负责 supersede 同空间活动 Run、递增 generation、清理该空间可重建知识并创建新的 force Run。

应用回退只允许停止新 Worker、保留数据库 Run/RunPage checkpoint 后修复并重新部署新版本；不恢复旧空间编译协议。Schema migration 保持 additive，避免应用修复期间破坏已经记录的新 Run 状态。

- [ ] artifact ID 和唯一键包含 workspace/space scope；相同 canonical key 的两个空间不会共享或互相修改 artifact。
- [ ] 新 Run 不再创建逐页文字 BullMQ Job。
- [ ] 最终模块不再生产或消费旧逐页文字、逐页 merge、旧 aggregate 空间 Job，只运行新空间协议。
- [ ] 所有空间共享图片队列，每个物理 Job 只处理一张图，结果按 run/page/attachment version 正确归属。
- [ ] 单图 Job payload 只携带 RunImage identity；dispatcher 不重新导出页面，Worker 从 DB 读取冻结 ordinal/metadata/alt text/source fence。
- [ ] 非复用页的 cache hit 图在 init 时落 succeeded RunImage，复用页无 RunImage 且不被子行重算；父图片 counters 不倒退。
- [ ] 图片结果完成后只推进一次 `queued/image_merge`；merge continuation 可以有多个物理 Job，但同一时刻最多一个有效 sequence。
- [ ] 页面在活动 Run 期间修改不会丢失，最终存在 incremental follow-up Run。
- [ ] 普通请求遵守 create/coalesce/rerun 三分支且不无条件 supersede；source-set 删除会 fail-closed 重置旧 plan，不能重新暴露删除内容。
- [ ] `initializeRun()` 排除当前 queued Run 并跳过 failed/superseded 候选，aggregate 全量复用能够真实命中上一个完成 Run。
- [ ] 全量复用请求允许 API 先返回 created/queued，再由初始化 lease 直接 `finishRun()`；状态机和 Diagnostics 对该短暂尖峰解释一致。
- [ ] 所有自然 `succeeded/partial/failed` 终态只能通过 lease-bound `finishRun()`；force supersede 是唯一明确例外。
- [ ] REST/page listener 与 Hocuspocus `PAGE_CONTENT_UPDATED` 共用同一空间 Run 请求语义，后者仍保留 access reindex。

可靠性验收：

- [ ] 任意实例退出不会让 Run 永久停留在 running。
- [ ] OS env/Consul 在动态 import AppModule 前可用，开发 `.env` 由保留 `expandVariables` 的 ConfigModule 加载；`jest.isolateModules()` 的非默认 decorator 配置测试通过，非法值不会静默回退。
- [ ] 空间 Worker 显式配置 lock/stalled 参数，续锁失败和 stalled 有指标/日志/告警；同一队列所有实例配置同构。
- [ ] 所有多表编译事务遵守 `spaces -> Run -> RunPage -> RunImage`，不使用 join `FOR UPDATE` 暗示锁序。
- [ ] 空间页面硬 deadline 为 15 分钟、aggregate 总 deadline 为 5 分钟，默认空间槽最坏 25 分 5 秒内让出；单图 active 占槽不超过 3 分钟。
- [ ] 启动时满足 `2 * KNOWLEDGE_COMPILER_TIMEOUT_MS + 60000 <= KNOWLEDGE_AGGREGATE_DEADLINE_MS`；aggregate 首次/repair 请求共享阶段 deadline。
- [ ] 最终 failed 事件和“过期 lease + exact Job 终态”能通过 recovery lease + `finishRun()` 收敛；单独 lease expiry 不误杀仍 active/retryable 的 Job。
- [ ] 空间 exact Job missing 最多有界重排队 3 次，恢复耗尽仍只能经 recovery lease + `finishRun()` 终态化。
- [ ] 接管后已完成页面不会重新调用 LLM。
- [ ] 旧 execution token 不能发布。
- [ ] 图片 Worker、outbox 和 force/reset 使用各自 generation/status/jobId CAS，不错误依赖已释放的空间 execution token。
- [ ] Redis 短暂不可用或投递 ack 丢失时，数据库中 `dispatched_at IS NULL` 的 queued 记录能由 reconciler 使用确定性 Job ID 重新投递并补写 ack。
- [ ] 图片队列不使用 `removeOnComplete/removeOnFail: true`，completed/failed exact Job 在 processing expiry + reaper 窗口内可查。
- [ ] 单图 processing 有独立 expiry，retry 能刷新，reaper 在 expiry 后根据 exact Job 状态终结或最多重投 3 次，不误杀仍可执行/重试的 Job。
- [ ] RunImage 失败持久化 retryable/permanent 分类，父 `image_status` 和 `merge_status` 只从 DB 子行终态推导，不依赖进程内计数。
- [ ] attachment version 比较统一截断到毫秒，不因 PostgreSQL 微秒精度产生假 image_changed。
- [ ] 单页永久失败不阻断其余页面。
- [ ] 图片部分失败时成功结果仍能合并，Run 为 partial。
- [ ] force Run 的自动 follow-up 为同 generation 的 incremental；显式 force 才 generation+1 并清理。
- [ ] `DATABASE_MAX_POOL` 已显式配置且满足本实例 `space + image + 10` 预算；全部进程池总和加保留量不超过 PostgreSQL `max_connections`。
- [ ] removed source 在 request/delete 入口先使受影响 artifact/chunk 和 active overview 不可检索，contribution 只在初始化时物理删除；初始化失败也不会保留可见的删除内容。

性能与可观测性验收：

- [ ] 大空间不会一次向 Redis 投递全部文字页面。
- [ ] source exporter、空间 access reindex 和 embedding rebuild 使用稳定 keyset/batch checkpoint；5000 页/大量 chunks 不进入单条无 LIMIT 查询或一个全空间更新事务。
- [ ] import 的 embedding 在途并发不超过 2、单批不超过 50、单请求不超过 30 秒；provider/import/vector/retrieval 四个调用点均传递取消信号。
- [ ] 明确记录并接受同空间固定串行可能增加单个大空间端到端耗时；第一版不以重新引入 canonical 并发作为优化手段。
- [ ] 100 个大空间中，continuation 不会越过已经等待的同优先级首次时间片，空间槽不存在单 Run 数小时连续占用。
- [ ] 多 dispatcher 并发时，单 Run 的 DB `RunImage queued + processing` 仍不超过 5。
- [ ] Diagnostics summary 不读取全部 RunPages。
- [ ] Run 和 RunPage 列表均数据库分页。
- [ ] 主页面不依赖扫描大量 Redis Job payload。
- [ ] Diagnostics 将 Worker 数、space/image capacity 标为 estimate；`CLIENT LIST` 不可用时显示 unknown，且这些值不参与调度。
- [ ] Diagnostics 展示 DB 待确认/补投数量、空间 Worker lock/stalled 配置及最近续锁失败/stalled 事件。
- [ ] Diagnostics 单独展示 waiting initialization 和 `page_timeout` 预算终态，不把全量复用排队尖峰或复杂页预算超时误报为系统故障。

## 16. 最终架构原则

本方案最终形成三个清晰边界：

```text
调度边界：空间阶段时间片
  一个执行槽处理一个空间阶段的可恢复时间片；5 页/5 分钟安全让出，实例增加时空间并发增加。

知识一致性边界：空间
  同空间的文字和图片增强知识逐页串行发布；不同空间完全并行。

图片计算边界：单图
  所有空间共享图片队列；每个 Job 只处理一张图；RunImage 落库并聚合页面/空间屏障后再串行合并。
```

它避免了 100 个物理队列、100 个实例、空间 Worker 绑定和全局调度器，同时继续复用现有数据库状态机、outbox、图片缓存与发布 fencing。这是一次性切换下边界清晰、可恢复且可验证的新编译协议，不以保留旧路径或追求代码 diff 最小为目标。
