# 权限模型

本文描述 Akasha 的访问控制模型：有哪些凭证、每种凭证对应什么身份、身份如何落到空间和页面上。只描述当前实现。

---

## 判定链

一次请求依次经过五层，任一层不通过即拒绝：

```
凭证 → 身份 → 端点凭证策略 → 空间范围 → 空间角色 → 页面限制
```

- **凭证**：请求携带的身份证明
- **身份**：凭证解析出的主体，**恒为真实用户**
- **端点凭证策略**：个人密钥受 HTTP 黑名单限制，带 Agent 密钥时还须通过 Agent 端点白名单。
- **空间范围**：Agent 密钥的绑定集合。普通接口与本人空间关系取**交集**，知识查询接口取**并集**
- **空间角色**：在某个空间内的角色，决定该空间的基础能力
- **页面限制**：单个页面的额外收紧，可覆盖空间角色

## 凭证

| 凭证 | 作用 | 位置 |
| --- | --- | --- |
| 会话凭证 | 身份：真实用户 | Cookie |
| 个人 API 密钥 | 身份：真实用户，可设过期时间 | `Authorization: Bearer` |
| SSO 令牌 | 身份：真实用户（含数字员工） | `x-token` |
| Agent API 密钥 | **不构成身份**，只提供空间范围 | `x-akasha-public-key` |

**Agent 密钥不是凭证意义上的身份来源。** 它不过期、可轮换，轮换后旧密钥立即失效。放进 `Authorization` 头会被明确拒绝（`Agent API keys cannot authenticate a request`），只有专用请求头会被接受。请求头位置在这里是机制，不是约定。

密钥不携带页面级权限，只携带空间范围。除知识查询外，带密钥的请求能做什么完全由本人的权限决定；密钥决定的是在哪些空间内、通过哪些接口。

### 凭证组合

| 组合 | 结果 |
| --- | --- |
| 仅会话／个人密钥／SSO 令牌 | 真实用户身份 |
| 仅 Agent 密钥 | **401**，没有身份可用 |
| 个人密钥 + Agent 密钥 | 真实用户身份 + 空间范围 |
| SSO 令牌 + Agent 密钥 | 真实用户身份 + 空间范围 |
| 个人密钥 + SSO 令牌 | **401**（`Unsupported credential combination`） |

身份槽（会话／Bearer／`x-token`）与范围槽（`x-akasha-public-key`）互不冲突，但身份槽内部互斥：`x-token` 和 `Authorization` 同时出现直接拒绝。

少数外部集成接口要求必须带 Agent 密钥（见下文端点表的 ※ 标记），缺少时返回 401。

## 身份

身份恒为真实用户，有工作区角色：所有者、管理员、成员。

- 工作区所有者和管理员在空间层面被直接视为空间管理员，不需要空间成员关系
- 空间关系来自两个来源：直接成员，以及通过用户组间接成为成员；取其中最高角色
- 所有者跳过全部页面限制检查

SSO 令牌有两种验证路径：普通用户令牌，以及带 `x-iself-agent: 1` 的数字员工令牌。两者都按邮箱落到一个**普通用户行**上，解析出的身份没有区别。

### Agent 用户行

每把 Agent 密钥在创建时会生成一个 `userType = 'agent'` 的用户行，邮箱形如 `agent-user-<id>@akasha.net`，工作区角色为成员。绑定空间时会同步写入该行的空间成员关系（角色为阅读者）。

**这个用户行不参与任何权限判定。** 它的存在只有两个用途：

- 使用统计中的操作者归因（`actor_id`）
- `api_keys.agent_user_id` 外键和密钥重名校验

空间绑定关系的权威来源是 `api_key_spaces` 表，不是这个用户行的成员关系。

## 个人 API 密钥的 HTTP 黑名单

个人密钥可通过 Bearer 认证普通 HTTP 请求和 `/mcp`。HTTP 请求以持有者的用户身份执行，仍需通过各接口的资源授权。下列端点在进入业务处理前拒绝个人密钥，返回 403（`PERSONAL_API_KEY_FORBIDDEN`）。

| HTTP 端点 | 受限操作 |
| --- | --- |
| `/api/api-keys` 管理控制器的全部端点 | 列出、创建、修改、轮换、撤销密钥，以及管理 Agent 的空间范围 |
| `POST /api/auth/change-password` | 修改密码 |
| `POST /api/auth/collab-token` | 签发协同令牌 |
| `POST /api/sessions/revoke`、`POST /api/sessions/revoke-all` | 撤销会话 |
| `POST /api/users/update` | 修改账号资料 |

## Agent 端点白名单

带 Agent 密钥的请求只能调用显式声明了 `@AgentCallable` 的接口，其余一律 403（`Agent API key cannot call this endpoint`）。守卫只检查声明是否存在，**不校验声明的能力名与接口实际行为是否一致**。

当前开放的接口：

| 接口 | 声明的能力 |
| --- | --- |
| `POST /api/pages/info` | `page.read` |
| `POST /api/pages/search` | `page.read` |
| `POST /api/pages/sidebar-pages` | `page.tree.read` |
| `POST /api/pages/create` | `page.create` |
| `POST /api/pages/update` | `page.content.update` |
| `POST /api/files/upload` | `attachment.upload` |
| `POST /api/spaces/` | `space.read` |
| `POST /api/spaces/info` | `space.read` |
| `POST /api/llm-wiki/query` | `knowledge.query`（仅 robot 模式） |
| `POST /api/llm-wiki/citation-page` | `page.read` |
| `POST /api/iself/space` | `space.read` |
| `POST /api/iself/llm-wiki/query` ※ | `knowledge.query` |
| `POST /api/iself/space-api-key/update` ※ | `space.binding.update` |

※ = 必须携带 Agent 密钥。

### 知识查询凭证

| 凭证 | `POST /api/llm-wiki/query` 的 `type=robot` | `POST /api/iself/llm-wiki/query` |
| --- | --- | --- |
| 仅个人密钥 | 本人可读空间 | 401，缺少 Agent 密钥 |
| 仅会话或 SSO | 401，缺少 Agent 密钥 | 401，缺少 Agent 密钥 |
| 会话、SSO 或个人密钥搭配 Agent 密钥 | 本人可读空间与绑定空间的并集 | 同左 |
| 仅 Agent 密钥 | 401，缺少用户身份 | 401，缺少用户身份 |

两个 robot 查询入口共用检索、页面授权、引用、附件与审计逻辑。通用知识兜底由请求字段 `generalKnowledgeEnabled` 显式开启。普通查询默认使用 `type=user`，携带 Agent 密钥时返回 400。

**MCP（`/mcp`）不接受 Agent 密钥**，连接时即返回 401。MCP 只支持个人密钥和 SSO 令牌。

白名单之外的接口（含 `pages/delete`、`pages/restore`、`pages/move-to-space`、`pages/move`、`pages/duplicate`、页面权限管理、评论等）带 Agent 密钥一律 403。

> 带 Agent 密钥是**整个请求**降到白名单内，不是「只有 Agent 相关逻辑受限」。同一个人用个人密钥能调 `pages/delete`，加上 Agent 密钥后同一请求会 403。客户端若把密钥固定配在所有请求上，会连本人原有的能力一起失去；要混用必须按接口决定是否发送该头。

> 守卫只检查声明是否存在，不校验能力名与接口实际行为是否一致。能力名只进使用统计的 `op` 字段。

## 空间范围

每把 Agent 密钥绑定一组空间。该集合如何参与判定，**取决于接口类型**：

### 普通接口：交集

页面、空间、附件等接口，有效范围是**绑定集合与本人空间关系的交集**：

| 空间状态 | 结果 |
| --- | --- |
| 已绑定 + 本人是成员 | 可访问 |
| 已绑定 + 本人不是成员 | 拒绝 |
| 未绑定 + 本人是成员 | 拒绝 |
| 两者都无 | 拒绝 |

密钥只收窄范围。本人在范围内的权限与不带密钥时完全一致——读、写、`canEdit` 全由本人的空间角色和页面授权决定。

### 知识查询接口：并集

`llm-wiki/query` 和 `iself/llm-wiki/query` 是唯一的例外。密钥的绑定空间在检索时**追加**到本人的可读范围上：

| 空间状态 | 结果 |
| --- | --- |
| 已绑定 + 本人是成员 | 可检索 |
| 已绑定 + 本人不是成员 | **可检索**（密钥扩展） |
| 未绑定 + 本人是成员 | 可检索（本人权限） |
| 两者都无 | 检索不到 |

绑定空间跳过空间角色检查，但**不跳过页面限制**：该空间内的受限页面仍需本人有自己的授权。所以密钥扩展的是空间层的触达，不是页面层的授权。

这两个接口不再预检「请求的空间是否都在密钥范围内」——范围外但本人能读的空间照常可用，两者都不满足的空间检索为空。

- 只有非个人空间可被绑定，个人空间永不可绑
- 绑定由该空间的管理员（或工作区所有者）通过 `POST /api/iself/space-api-key/update` 修改，发起人必须是每个目标空间的管理员
- 列表类接口按该范围过滤

不带 Agent 密钥的请求没有空间范围概念，直接使用本人的空间关系。

## 空间角色

角色构成一条链，能力逐级包含：

```
无 < 阅读者 < 写入者 < 空间管理员
```

| 角色 | 空间设置 | 成员管理 | 页面 | 分享 |
| --- | --- | --- | --- | --- |
| 空间管理员 | 管理 | 管理 | 管理 | 管理 |
| 写入者 | 只读 | 只读 | 管理 | 管理 |
| 阅读者 | 只读 | 只读 | 只读 | 只读 |

空间有「公开／私有」可见性字段，但当前没有任何判定读取它，也没有「加入空间」的入口。空间可见性完全由成员关系决定。

## 页面限制

页面默认继承空间角色。页面也可以单独设限，且沿页面层级向下继承：

- 判断一个受限页面是否可见，要看从它到根的整条路径上**每一个设了限制的层级**是否都单独授权过。漏掉任何一层即不可见。
- 是否可编辑，由**最近**的那个受限层级上的最高角色决定，不是整条路径取交。
- 授权可以直接授予个人，也可以授予用户组。
- 工作区所有者跳过全部页面检查。

带 Agent 密钥时，这一层的判定主体仍是本人，与不带密钥时相同。受限页面本人有编辑授权即可写入，密钥不额外收紧。接口返回的 `canEdit` 描述的是本人的真实编辑权限。
